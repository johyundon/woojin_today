# API 명세 정리 (Part E: 포털 로그인 + 오늘의 학식)

출처: 노션 "Flutter 기록 / Request/Response (1)" 데이터베이스의 페이지 3개 (`(로그인-userId)(1)`, `(로그인-userId)(2)`, `(오늘의 학식)`). Part A~D에 빠져 있던 3개 API다.
공통 사항:

- User-Agent는 `Mozilla/5.0 (Linux; Android 14; Mobile) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/128.0.0.0 Mobile Safari/537.36` 로 고정.
- 노션 속성: 모든 페이지가 `API 분류=API Response`, `태그=DTO(요청 객체)`.
- 두 로그인 페이지는 같은 로그인 흐름을 다룬다. (1)은 로그인 API 중심(폴백은 6번에 요약), (2)는 로그인 + 폴백 API를 별도 API로 나눠 설명한 버전이다. 여기서는 하나로 합쳐 정리했다.

### 1. 로그인 (userId) - 포털 로그인

- 노션: https://app.notion.com/p/6583c48d630d83c38c4181fb4f990e57 , https://app.notion.com/p/b923c48d630d82b9b0e00169a946e7e1
- **메서드/주소**: `POST https://www.daejin.ac.kr/subLogin/daejin/login.do`
- **요청 헤더**: `Content-Type: application/x-www-form-urlencoded;charset=UTF-8`, `User-Agent`(위 고정값)
- **쿼리 파라미터**: 없음
- **요청 본문(form)**:

| 필드             | 값           | 의미                                                |
| ---------------- | ------------ | --------------------------------------------------- |
| layout           | (빈값)       | 미사용, 항상 빈 문자열                              |
| pwdCrtfcNo       | (빈값)       | 미사용                                              |
| pwdInputExcessYn | (빈값)       | 미사용                                              |
| userId2          | (빈값)       | 서버가 응답 후 발급하는 값이라 요청에서는 항상 비움 |
| userId           | `{학번}`     | `URLEncoder.encode(값, "UTF-8")` 적용               |
| userPwd          | `{비밀번호}` | `URLEncoder.encode(값, "UTF-8")` 적용               |

- **HTTP 클라이언트 필수 요건**:
  1. 리다이렉트 자동 추적 ON.
  2. 이 로그인 전용의 격리된 쿠키 저장소를 **매 로그인 시도마다 새로** 만든다. 앱 공용 쿠키와 섞이면 이전 시도의 쿠키가 새어 들어갈 수 있음. 이 저장소는 아래 2번(폴백) 호출까지 그대로 재사용.
  3. 리다이렉트 체인의 모든 중간 응답(Set-Cookie/Location 헤더)을 모을 수 있어야 함 (예: OkHttp `response.priorResponse`). 최종 응답만 보면 안 됨.
- **응답 형태**: 단일 응답이 아니라 `login.do` → 302 → (SSO 처리) → 302 → … → 최종 200 으로 이어지는 리다이렉트 체인. 필요한 값이 체인의 서로 다른 홉에 흩어져 있음.
  - 비밀번호를 6개월 넘게 바꾸지 않은 계정은 중간에 "6개월간 변경하지 않았습니다" 안내 페이지 홉이 끼고, 이 경우 체인 안에서 `uid`가 바로 나옴.
- **응답 처리(파싱) 규칙**:
  - **WMONID / JSESSIONID**: 체인 모든 홉의 `Set-Cookie`를 모아 정규식 `WMONID=(.*?);`, `JSESSIONID=(.*?);` 의 첫 매치 사용.
  - **userId2 (SSO uid)**: 체인 모든 홉의 `Location` 헤더를 순서대로 검사.
    - 헤더에 `uid%253D` 포함 → URL 디코딩 1회 후 정규식 `uid%3D(.+?)(?:%26|&|$)` 적용, 매치되면 확정.
    - 아니고 `uid%3D` 포함 → 디코딩 없이 같은 정규식 적용, 매치되면 확정.
    - 둘 다 아니면 다음 홉. 안내 페이지 경로 여부에 따라 인코딩이 1회/2회로 달라지므로 미리 판단하지 말고 두 패턴을 모두 검사.
    - 모든 홉에서 못 찾으면 2번(폴백) 실행.
  - **성공/실패 판정**(최종 응답 바디 HTML):
    - `회원정보이(가) 존재 하지 않습니다` 포함 → 실패: 존재하지 않는 계정
    - `입력하신 계정정보가 올바르지 않습니다` 포함 → 실패: 비밀번호 오류. 정규식 `(\d+)회\s*더\s*잘못입력`으로 잔여 입력 횟수 추출 가능
    - 둘 다 없으면 성공
    - 실패면 WMONID/JSESSIONID/userId2 추출은 의미 없으니 바로 실패 반환
  - **최종 산출물**: `{ wmonid: String?, jsessionId: String?, userId2: String? }` (userId2는 1번 체인 또는 2번 폴백에서 추출, 둘 다 실패하면 null)
- **응답 예시**: 페이지에 없음.
- **특이사항/주의**:
  - 이후 dreams2 계열 API는 `Cookie: userId={userId2}; orgCd={고정 상수}` 형태로 호출. `orgCd`는 앱 전역 고정 상수(값은 노션 원문 참고, 이 문서에서는 옮기지 않음).
  - userId2가 null이면 로그인 자체는 성공이지만 프로필·졸업학점·지도교수 등 dreams2 API는 동작하지 않음.
  - 2번 폴백에 대해 (1) 페이지는 "6개월 안내가 안 뜬 경우 여기로 옴"으로, (2) 페이지는 "이미 비밀번호를 변경한 계정이라 안내가 필요 없는 경우 필수"로 같은 조건을 다르게 표현함.

### 2. 로그인 폴백 (uid를 못 찾았을 때만) - dreams2 LinkPortal

- 노션: 위 1번과 동일 (`(로그인-userId)(1)`의 6번 항목, `(로그인-userId)(2)`의 API 2)
- **호출 조건**: 1번 체인에서 `uid`를 못 찾았을 때. "있어도 되고 없어도 되는 예외 처리"가 아니라 이 조건에서는 필수 단계.
- **메서드/주소**: `GET https://dreams2.daejin.ac.kr/sugang/LinkPortal.jsp?dvd=P`
- **요청 헤더**: `Referer: https://www.daejin.ac.kr/`, `User-Agent`(위 고정값)
- **요청 본문**: 없음. **쿼리 파라미터**: `dvd=P` (고정)
- **HTTP 클라이언트 필수 요건**:
  - 1번 로그인에 쓴 **동일한 쿠키 저장소**를 그대로 재사용. 새 저장소에 WMONID만 심어 호출하면 nsso가 "방금 로그인한 세션"으로 인식하지 못하고 튕겨냄.
  - 리다이렉트 추적 ON.
- **응답 처리(파싱) 규칙**:
  - 리다이렉트 체인 모든 홉의 `Set-Cookie`에서 정규식 `^userId=([^;]*)` 매치.
  - 여러 번 매치되면(자리표시자 값 → 실제 값 순서로 2번 올 수 있음) **마지막 매치**를 userId2로 사용.
  - 이것도 실패하면 userId2 = null, 로그인은 성공 처리(WMONID/JSESSIONID는 유효).
- **응답 예시**: 페이지에 없음.
- **특이사항/주의**: 기존 기록에 따르면 이 폴백은 nsso 리다이렉트로 dreams2 전용 세션 쿠키를 새로 발급받는 흐름이며, 과거 이 쿠키가 무시되던 버그를 수정한 이력이 있음(개발 중 확인한 내용, 노션 페이지에는 없음).

### 3. 오늘의 학식

- 노션: https://app.notion.com/p/dac3c48d630d8207804f011d83f79cf1
- **메서드/주소**: `POST https://www.daejin.ac.kr/diet/daejin/2/view.do`
- **요청 헤더**: `Content-Type: application/x-www-form-urlencoded; charset=UTF-8`, `User-Agent`(위 고정값)
- **쿼리 파라미터**: 없음
- **요청 본문(form)**:

| 필드   | 값                              | 의미                                                                                              |
| ------ | ------------------------------- | ------------------------------------------------------------------------------------------------- |
| monday | `yyyy.MM.dd` (예: `2026.09.07`) | 조회할 주의 월요일 날짜. 서버는 이 날짜가 속한 주(월~일) 전체를 돌려줌                            |
| week   | (빈값)                          | 항상 빈 문자열. 노션 Body 예시에는 `week=next`가 적혀 있으나 프롬프트는 "빈값 고정"이라 서로 다름 |

- **응답 형식**: HTML 페이지 하나 (`<meta charset="UTF-8">`).
- **응답 처리(파싱) 규칙**:
  1. 셀렉터 `div.box-table table`로 표를 찾는다. 표가 없으면 에러 대신 월요일부터 7일 전부 "메뉴 없음" 빈 데이터로 채워 반환.
  2. `thead`의 `th` 중 첫 번째(식단구분) 제외 7개에서 요일별 날짜 추출. 정규식 `\d{4}\.\d{2}\.\d{2}`. 못 찾으면 요청 `monday` + 요일 인덱스를 날짜로 대체.
  3. `tbody`의 `tr`을 순서대로 순회:
     - `th`가 있는 행: 텍스트에 `조식` → 조식, `중식` 또는 `점심` → 중식, `석식` 또는 `저녁` → 석식으로 "현재 섹션" 갱신. 그 외 텍스트면 섹션을 null로.
     - `th`가 없는 행: 직전 "현재 섹션" 유지(같은 끼니에 코너가 여러 줄).
     - 현재 섹션이 null이면 행 건너뜀.
     - `td`를 순서대로 최대 7개(8번째부터 무시) 각 요일 인덱스에 매핑해 4번 규칙으로 파싱.
  4. 셀 파싱:
     - `class="no-data"`면 항목 없음(스킵).
     - 셀 안 텍스트 노드 중 공백이 아닌 첫 번째를 "메뉴 원문"으로 사용. 없으면 스킵.
     - 원문이 `[`로 시작하면 정규식 `^\[(.+?)]`의 괄호 안 내용을 코너 이름으로 뽑고 원문에서 제거. 괄호가 없으면 코너 기본값 `학생회관`.
     - 남은 텍스트의 앞뒤 공백 제거 → 앞뒤 `/` 제거 → 남은 `/`는 모두 `·`로 치환.
     - 셀 안에 `span`이 있으면 그 텍스트에서 정규식 `가격\s*:\s*(.+?)]`로 가격 추출(없으면 null).
     - 결과 `{코너, 메뉴텍스트, 가격}`을 해당 요일의 해당 끼니 리스트에 추가.
  5. **최종 산출물**: `[ { date, breakfast: [{corner, menu, price}], lunch: [...], dinner: [...] }, ... 7일치 ]`
- **응답 예시(발췌)**: 식단기간 `2026.09.14 ~ 2026.09.20`, 헤더 `<th scope="col">월<br>2026.09.14</th>` 형태, 조식/점심 행의 모든 `td`가 `<td class="no-data">등록된 식단내용이(가) 없습니다.</td>`. 식단이 있는 셀의 실제 HTML 예시는 페이지에 없음.
- **특이사항/주의**:
  - 응답 예시의 행 제목은 `조식`/`점심`뿐이고 `석식`/`저녁` 행은 없음 → 석식이 없는 주에는 석식 리스트가 비게 됨(추정).
  - 헤더가 5개 `col` 정의(`colgroup`)인데 실제 열은 8개(식단구분+7일). 파싱은 `colgroup`이 아니라 `th`/`td` 기준.
  - 요약 문서(`API_명세_정리.md`)에 따르면 받아온 주간 데이터는 캐시하고 일주일이 지나기 전엔 재요청하지 않음(노션 API 표 기준).
  - 로그인/쿠키 불필요.

## 페이지 간 모순/특이점 요약

1. 학식 `week` 필드: Body 예시 `week=next` vs 프롬프트 "빈값 고정".
2. 로그인 폴백 호출 조건 설명이 (1)·(2) 페이지에서 표현만 다르고 의미는 같음.
3. 학식 응답 예시에 실제 메뉴가 담긴 셀이 없어 코너·가격 파싱 규칙은 예시로 검증할 수 없음.
4. 로그인 페이지에는 응답 예시가 없음.
