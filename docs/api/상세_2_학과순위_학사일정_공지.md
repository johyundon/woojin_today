### 1. 학과순위 - T-WIN 로그인
- **메서드/주소**: `POST https://together.daejin.ac.kr/login/a/n/loginProc.do` (T-WIN 자체 로그인. 포털 www.daejin.ac.kr 로그인, 수강신청 dreams2.daejin.ac.kr 로그인과 별개)
- **요청 헤더**:
  ```
  Content-Type: application/x-www-form-urlencoded; charset=UTF-8
  Origin: https://together.daejin.ac.kr
  Referer: https://together.daejin.ac.kr
  User-Agent: (위 공통값)
  ```
- **요청 본문/쿼리 파라미터** (쿼리 파라미터는 없음)

  | 필드 | 값 | 의미 |
  |---|---|---|
  | targetUrl | `%2FclientMain%2Fa%2Ft%2Fmain.do` (디코딩하면 `/clientMain/a/t/main.do`) | 고정값. 로그인 성공 후 이동할 목적지로 추정됨(페이지에도 "추정"으로 적힘) |
  | userId | `{학번}` | URLEncoder.encode(값, "UTF-8") 적용 |
  | userPw | `{비밀번호}` | URLEncoder.encode(값, "UTF-8") 적용 (필드명이 userPw) |
- **응답 형식**: 본문은 파싱하지 않음. 인코딩 표기: 페이지에 없음.
- **응답 처리(파싱) 규칙**:
  1. 리다이렉트를 모두 따라간 뒤 최종 응답의 상태 코드가 2xx인지 확인한다.
  2. 최종 URL의 path에 문자열 `/login/`이 포함되는지 확인한다.
  3. (1)이 참이고 (2)가 거짓이면 로그인 성공.
  4. 그 외(2xx가 아니거나, 최종 path에 `/login/`이 남아 있음)는 로그인 실패.
  5. 이 API가 돌려주는 데이터는 없다. 판정 규칙이 전부다.
- **응답 예시**: 페이지에 없음 (본문을 파싱하지 않는 API)
- **특이사항/주의**:
  - 리다이렉트 자동 추적 필수.
  - 로그인 전용 쿠키 저장소 필요: 호스트별 저장, 같은 이름의 쿠키가 다시 오면 교체, 요청 시 만료 안 된 쿠키만 전송. Cookie 헤더를 직접 세팅하지 않고 클라이언트의 쿠키 저장소에 맡긴다.
  - 이 쿠키 저장소를 이후 모든 T-WIN API(평점, 동기 평점 비교, 마일리지현황, 지도교수상담 등)에서 그대로 재사용해야 한다. 클라이언트를 화면마다 새로 만들면 로그인도 매번 새로 해야 한다.
  - Body 예시 코드블록은 `&` 뒤에 줄바꿈이 있는 형태로 적혀 있으나, 프롬프트에는 한 줄 `targetUrl=...&userId=...&userPw=...` 형태로 설명됨. 줄바꿈은 표기용으로 보임(추정).
  - 헤더 코드블록은 줄바꿈이 없이 붙어 보이는 형태(`...charset=UTF-8Origin: ...`)로 저장되어 있음. 노션 변환 과정의 표기 문제로 보이며 헤더는 위처럼 4개로 해석함(추정).

### 2. 학과순위 - 평균성적(내 평점) 불러오기
- **메서드/주소**: `POST https://together.daejin.ac.kr/myFuture/a/n/getResultDivInfoPage.do`
- **요청 헤더**:
  ```
  Content-Type: application/x-www-form-urlencoded; charset=UTF-8
  IS_AJAX: isAjax
  X-Requested-With: XMLHttpRequest
  Origin: https://together.daejin.ac.kr
  Referer: https://together.daejin.ac.kr/myFuture/a/m/myFutureView.do
  User-Agent: (위 공통값)
  ```
- **요청 본문/쿼리 파라미터** (쿼리 파라미터는 없음)

  | 필드 | 값 | 의미 |
  |---|---|---|
  | sustCd | `{학과코드}` | 호출하는 쪽이 넘기는 값(고정 아님). 응답 예시 속 JS에는 `AA0194`가 나옴 |
  | shyrCd | `{학년코드}` | 호출하는 쪽이 넘기는 값(고정 아님). 정확한 학년코드를 모르면 `"3"`을 대신 넣어도 됨. 이 앱이 실제로 쓰는 fallback일 뿐 API가 3을 요구하는 것은 아님 |
  | pageIndex | `1` | 고정 |
  | searchType | `STD_GROUP` | 고정 |
  | roadMapType | `SAMEGRADE` | 고정 |
- **응답 형식**: HTML. 인코딩: 페이지에 없음.
- **응답 처리(파싱) 규칙**:
  1. HTML에서 `li.grade_my` 아래의 `strong` 태그 텍스트를 찾는다.
  2. 그 텍스트를 실수(소수)로 변환한 값이 평점이다.
  3. 요소가 있고 실수로 변환되면 성공(평점 리턴). 요소가 없거나 변환 불가면 실패 (보통 로그인 세션 만료 또는 sustCd/shyrCd 오류).
  4. 네트워크 자체 실패(타임아웃 등)는 별도로 구분해 처리.
  5. 최종 산출물: 평점 실수 하나, 또는 실패.
- **응답 예시** (발췌):
  ```html
  <ul class="grade_detail">
    <li class="grade_my"><p>내 성적</p><strong>4.34</strong></li>
    <li class="grade_same"><p>동일 학년</p><strong>3.23</strong></li>
  </ul>
  ```
  응답 뒤쪽 `<script>`에는 apexcharts 옵션(내 점수 4.34, 동일 학년 3.23)과, 같은 학년 목록을 불러오는 ajax 코드(`https://together.daejin.ac.kr:443/myFuture/r/n/getGrStdCompareListAjax.do`, 파라미터 sustCd/shyrCd/searchType=STD_GROUP/pageIndex)가 들어 있다. 이 ajax는 3번 API와 동일한 엔드포인트다.
- **특이사항/주의**:
  - 선행 조건: 1번 T-WIN 로그인 성공 + 같은 쿠키 저장소 재사용. 로그인 없이 단독 호출하면 실패한다고 적혀 있음.
  - 이 요청은 리다이렉트를 따라갈 필요가 없음(리다이렉트로 판단하지 않음).
  - 응답 예시에는 `li.grade_same strong`(동일 학년 평균 3.23)도 있으나, 페이지가 정한 파싱 대상은 `li.grade_my strong`뿐이다.
  - 응답 예시의 `li.grade_my`에는 내 성적(4.34)이 들어 있어 개인 성적 정보이나, 페이지 원문 예시 값이며 이름·학번 등은 없음.
  - 헤더 `IS_AJAX` 표기가 이 페이지에서는 대문자이고 3번 페이지 코드블록에서는 소문자 `is_ajax`임(3번 항목 참고).

### 3. 학과순위 - 같은 학과/학년 성적정보(동기 평점 비교 목록) 불러오기
- **메서드/주소**: `POST https://together.daejin.ac.kr/myFuture/r/n/getGrStdCompareListAjax.do` (주소 경로가 `/r/n/`이며, 2번의 `/a/n/`과 다름)
- **요청 헤더**:
  ```
  Content-Type: application/x-www-form-urlencoded; charset=UTF-8
  is_ajax: isAjax          (코드블록 표기. 프롬프트에서는 IS_AJAX: isAjax)
  X-Requested-With: XMLHttpRequest
  Origin: https://together.daejin.ac.kr
  Referer: https://together.daejin.ac.kr/myFuture/a/m/myFutureView.do
  User-Agent: (위 공통값)
  ```
- **요청 본문/쿼리 파라미터** (쿼리 파라미터는 없음)

  | 필드 | 값 | 의미 |
  |---|---|---|
  | sustCd | `{학과코드}` | 호출하는 쪽이 넘기는 값(고정 아님) |
  | shyrCd | `{학년코드}` | 호출하는 쪽이 넘기는 값(고정 아님) |
  | searchType | `STD_GROUP` | 고정 |
  | pageIndex | `{페이지 번호}` | 1부터 시작하는 정수. 페이지당 5명 |
- **응답 형식**: HTML (페이지당 표 1개). 인코딩: 페이지에 없음.
- **응답 처리(파싱) 규칙**:
  - 호출 순서(페이지네이션):
    1. `pageIndex=1`로 먼저 호출.
    2. 첫 응답 HTML 안의 JS 변수에서 전체 인원수를 정규식 `var\s+totalCnt\s*=\s*'(\d+)'` 로 추출. 못 찾으면 전체 인원수 0으로 취급.
    3. 전체 페이지 수 = ceil(전체 인원수 / 5). 인원수가 0이면 페이지 수 1로 취급하고 더 호출하지 않음.
    4. 페이지 수가 1보다 크면 `pageIndex=2`부터 마지막 페이지까지 모두 동시에(병렬로) 호출하고 모두 끝날 때까지 기다림.
    5. 페이지1, 페이지2, 페이지3... 순서대로 이어붙인 것이 최종 결과.
  - 페이지 하나당 파싱:
    1. `table tbody tr` 각 행에서 `td` 셀 중 0부터 센 인덱스 1번(두 번째 셀)의 텍스트를 뽑아 실수로 변환.
    2. 변환되지 않는 행은 건너뜀.
    3. 네트워크 자체 실패(타임아웃 등)는 별도로 구분.
  - 최종 산출물: 동기 평점 실수 목록(서버가 준 순서 그대로) + 전체 인원수(정수).
  - 페이지 크기 5는 API가 알려주는 값이 아니라 실제 호출로 확인된 고정 크기라고 적혀 있음.
- **응답 예시** (발췌):
  ```html
  <thead><tr><th>학과명</th><th>학점</th><th>비교과 프로그램 이수 횟수</th><th>자격증 개수</th><th>어학 개수</th><th>봉사활동 횟수</th></tr></thead>
  <tbody>
    <tr><td>컴퓨터공학전공</td><td>3.7</td><td>7</td><td>0</td><td>0</td><td>0</td></tr>
    <tr><td>컴퓨터공학전공</td><td>3.45</td><td>12</td><td>0</td><td>0</td><td>0</td></tr>
    ... (총 5행)
  </tbody>
  ...
  <script>
    var currentPage = '1';
    var totalCnt = '70';
    if(totalCnt) { fnCreatePageingView_std(totalCnt, 5, 5, currentPage, 'page_div_std') }
  ```
- **특이사항/주의**:
  - 선행 조건: 1번 T-WIN 로그인 성공 + 같은 쿠키 저장소 재사용.
  - 인덱스 1번 셀 = 표 헤더의 두 번째 열인 "학점" (예: 3.7, 3.45). 0번 열은 학과명 텍스트.
  - 예시의 `totalCnt = '70'`이면 페이지 수 14. 예시 HTML은 1페이지(5행)만 있음.
  - 페이지네이션 JS의 `fnCreatePageingView_std(totalCnt, 5, 5, ...)`에서도 5가 쓰이지만, 두 번째/세 번째 인자의 의미는 페이지에 설명 없음.
  - 이 응답에는 학생 이름 열이 없고, 본인이 몇 등인지 표시하는 정보도 없음(페이지에 없음). 순위는 호출하는 쪽에서 내 평점(2번)과 이 목록을 비교해 계산하는 구조로 보임(추정).
  - 헤더 표기 불일치: 코드블록은 `is_ajax`, 프롬프트는 `IS_AJAX`. 2번 페이지는 코드블록과 프롬프트 모두 `IS_AJAX`. HTTP 헤더 이름은 대소문자를 구분하지 않으므로 실질 영향은 없을 것으로 보임(추정).

### 4. 학사일정 조회 (월별)
- **메서드/주소**: `POST https://www.daejin.ac.kr/schdulmanage/daejin/19/monthSchdul.do`
- **요청 헤더**:
  ```
  Content-Type: application/x-www-form-urlencoded; charset=UTF-8
  User-Agent: (위 공통값)
  ```
- **요청 본문/쿼리 파라미터** (쿼리 파라미터는 없음)

  | 필드 | 값 | 의미 |
  |---|---|---|
  | year | `{연도}` | 조회할 연도(정수). 고정값 없음, 매번 호출 측이 전달 |
  | month | `{월}` | 조회할 월(정수). 고정값 없음, 매번 호출 측이 전달 |
- **응답 형식**: HTML. 인코딩: 페이지에 없음.
- **응답 처리(파싱) 규칙**:
  1. 셀렉터 `div.applyList table tbody tr` 로 행을 모두 찾는다.
  2. 각 행에서 `th` 텍스트를 "날짜 텍스트"로 가져온다. 없으면 건너뜀.
  3. `td` 텍스트를 "설명"으로 가져온다. 없거나 빈 문자열이면 건너뜀.
  4. 날짜 텍스트에서 정규식 `(\d{4})\.(\d{2})\.(\d{2})` 로 매치되는 날짜를 전부 찾는다 (yyyy.MM.dd, 한 줄에 여러 개 가능).
  5. 찾은 날짜가 없으면 그 행은 건너뜀.
  6. 첫 번째 날짜 = 시작일. 두 번째 날짜가 있으면 종료일, 없으면 시작일=종료일(하루짜리).
  7. `{시작일, 종료일, 설명}`을 항목으로 만들어 모든 행에 대해 반복한 목록이 최종 결과.
  8. 네트워크 자체 실패(타임아웃 등)는 별도로 구분.
  - 최종 산출물: `[{시작일, 종료일, 설명}, ...]`
- **응답 예시** (발췌):
  ```html
  <div class="applyList calList">
    <table>
      <tbody>
        <tr>
          <th scope="row" class="first last">2026.10.05(Mon)</th>
          <td class="first last">수업일수 1/3선<br></td>
        </tr>
        <tr>
          <th scope="row" class="first last">2026.10.20(Tue) ~ 2026.10.26(Mon)</th>
          <td class="first last">중간시험<br></td>
        </tr>
  ```
  응답에는 `month-search-box`(월 선택 UI, `jf_month('N')` 링크)와 달력 표(`<td class="sun">` 등 날짜 칸)도 함께 들어 있으나 파싱 대상이 아니다. 끝부분에는 HTML 주석으로 막아둔 연간 일정 영역(`yearSchdul`)이 있다.
- **특이사항/주의**:
  - 로그인 불필요. 쿠키 저장소/세션 유지 없이 단발성 요청.
  - 월 이동 시 year/month만 바꿔 처음부터 다시 호출하고, 캐시 없이 매번 새로 요청.
  - 날짜 텍스트 예시는 `2026.10.05(Mon)`처럼 요일이 붙고, 기간 일정은 `시작 ~ 종료`로 th 안에 줄바꿈과 함께 들어 있음. 정규식은 날짜 부분만 뽑는다.
  - 한 달 응답 안에서 여러 일정이 겹치는 기간(예: 2026.10.20~10.26 중간시험, 2026.10.20~11.01 중간 수업평가)도 별도 행으로 온다. 종료일이 다음 달로 넘어갈 수 있음.
  - 응답 예시는 2026학년도 10월분이며 "2026학년도 학사일정" 제목이 보임.

- **응답 처리(파싱) 규칙**:
  1. `table.board-table tbody tr` 로 행을 모두 찾는다.
  2. 각 행에서 `td.td-subject` 안의 `a` 태그를 찾는다. 없으면 건너뜀.
  3. 제목: `a` 안에 `strong`이 있으면 그 텍스트, 없으면 `a` 자신의 직접 텍스트(중첩 태그 제외). 앞뒤 공백 제거 후 비어 있으면 건너뜀.
  4. 작성자: `td.td-write` 텍스트.
  5. 날짜: `td.td-date` 텍스트.
  6. 조회수: `td.td-access` 텍스트.
  7. 첨부파일 여부: 행 안에 `td.td-file p.file-y`가 있으면 true, 없으면 false.
  8. 신규글 여부: `a` 안에 `span.new`가 있으면 true, 없으면 false.
  9. 상세경로: `a`의 href 그대로(도메인 없는 상대경로). 열려면 `https://www.daejin.ac.kr` + 값.
  10. 페이지네이션 없음: 이 응답 하나가 전부(추가 페이지 요청 없음).
  11. 네트워크 자체 실패(타임아웃 등)는 별도로 구분.
  - 최종 산출물: `[{제목, 작성자, 날짜, 조회수, 첨부여부, 신규여부, 상세경로}, ...]`
- **응답 예시**: **페이지의 응답 예시가 공지 게시판 HTML이 아니라 4번과 같은 월별 학사일정 달력 HTML**이다 (`month-search-box`, `2026학년도 학사일정`, `div.applyList calList` 표 등). `board-table`, `td-subject` 등 위 파싱 대상 태그는 응답 예시 안에 하나도 없다. 따라서 이 API의 응답 구조 예시는 페이지에 없다 (셀렉터 구조는 6번, 7번 페이지의 `board-table` 예시와 같은 사이트 공통 게시판 형식으로 추정).
- **특이사항/주의**:
  - 로그인 불필요하지만, 내부 SSO 인증 확인 때문에 302 리다이렉트가 여러 번(실측 4회) 발생. 각 홉에서 오는 쿠키(예: JSESSIONID)를 다음 요청에 계속 실어야 체인이 끝나고 최종 200이 옴.
  - 쿠키 없이 리다이렉트만 따라가면 `sso/checkToken.do?returnUrl=...&sso=ok` 근처를 맴도는 무한 루프에 빠짐(리다이렉트 한도를 걸어도 한도를 다 채우고 실패, 실측 확인됨).
  - 호스트별 쿠키 저장/재사용 쿠키 저장소가 필요. 로그인 세션은 불필요하고 이 요청의 리다이렉트 체인 안에서만 쿠키가 유지되면 됨. 같은 클라이언트를 재사용하면 쿠키 저장소도 계속 재사용되게 구현.
